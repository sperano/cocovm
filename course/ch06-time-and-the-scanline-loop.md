# Chapter 6 — Time: the scanline loop, sync pulses, and "it's alive"

*Week 6. Goal: understand `run_field()` — the heartbeat every other chapter
plugs into. Weeks 2–4 gave you a CPU that can execute any instruction
correctly; week 5 gave you a bus that resolves any address correctly. Neither
one, on its own, produces a running machine — a CPU with a bus is just a
function you can call, not something that boots. This week adds the missing
ingredient: a clock. By the end you will know exactly how many CPU cycles
fit in one scanline on real NTSC hardware, why the loop is built to be
paused and resumed one instruction at a time, and — the payoff — you'll
watch a real 1980s ROM boot to a prompt and answer `PRINT 2+2`, from cold
reset, with nothing but this loop driving it.*

---

## 6.1 Why an emulator needs a clock at all

Everything since week 1 has been about *correctness*: given an instruction
and a bus, produce the right result. Nothing so far has asked *when*.
`cpu.step(&mut bus)` doesn't know or care whether it's being called by a
test harness, a debugger's single-step button, or a video game running at
60 frames a second — it just executes one instruction and returns however
many cycles that cost. Called in a bare `loop {}`, it will execute billions
of instructions per second on modern hardware, because nothing is stopping
it. The real 6809E in a CoCo 3 executed 894,886 of them per second, no
more, no less, because its clock pin was wired to a crystal that oscillates
at a fixed rate. An emulator that just spins `cpu.step` in a tight loop
computes the right *values* in the wrong *amount of time* — which sounds
academic until you remember that everything a CoCo user could see or hear
was generated by watching those cycles go by: the video chip painted the
screen 60 times a second by counting cycles per scanline; the sound DAC's
waveform *was* a sequence of timed writes; keyboard debouncing assumed a
particular scan rate. Decouple cycle count from wall-clock time and the
machine you get isn't a fast CoCo, it's a different, wrong machine.

So something has to tie CPU cycles to real time. Two things, actually, and
they have to agree:

1. **The video hardware's own sync pulses.** Real CRT electronics need a
   horizontal sync pulse at the end of every scanline (to snap the electron
   beam back to the left edge) and a vertical/field sync pulse 60 times a
   second (to snap it back to the top). The CoCo's chips generate these
   pulses off the same crystal that clocks the CPU, and — this is the fact
   this chapter spends real time on — some of those pulses are wired
   directly into the CPU's interrupt lines. The 60 Hz field-sync interrupt
   isn't cosmetic; stock BASIC's main loop is *waiting* for it.
2. **The host's own real-time clock.** Whatever machine you're running the
   emulator on needs to present roughly 60 finished video fields per
   second to a human watching it, or the emulation feels wrong (too fast,
   too slow, choppy).

The scanline is the natural unit that satisfies both at once: it's small
enough to schedule video and audio work accurately (a real CoCo's picture
changes within a field, not just between fields — think of a screen split
effect, week 9's subject), and a whole field's worth of scanlines is
exactly the quantum the host's 60 Hz repaint wants. `DESIGN.md` §4 states
this design choice up front, and `crates/coco-core/src/machine/run.rs` is
where it actually lives. This chapter reads that file end to end.

> One clarifying note before we start: you will also see a method called
> plain `Machine::step()` (`crates/coco-core/src/machine.rs:241`) used in a
> few places — `examples/trace.rs`, `tests/boot.rs`,
> `tests/snapshot_roundtrip.rs`. It is *not* the loop this chapter is
> about. It's a one-line wrapper around `cpu.step(&mut self.bus)` with none
> of the scanline/interrupt/peripheral bookkeeping — useful for raw
> instruction-trace tooling that wants the CPU alone, dangerous for
> anything that needs the machine to actually run correctly (no interrupts
> will ever fire). Every real boot in this codebase goes through
> `run_field`/`step_instruction`, not `step`.

## 6.2 The numbers, derived

Before reading a single line of the loop, get the arithmetic in your head,
because the code is going to look like magic otherwise.

**The CPU clock.** From `crates/coco-core/src/machine.rs:24-26`:

```rust
/// NTSC CPU clock at normal speed: the 28.636363 MHz crystal / 32 (MAME
/// `coco3.cpp`). The SAM R1 bit doubles it (crystal / 16, ~1.79 MHz).
const CPU_HZ: f64 = 894_886.0;
```

That number should look familiar if you ever typed `PRINT PEEK(&HB000)` for
no reason as a kid — 0.895 MHz is the number every CoCo reference quotes.
It comes from dividing the NTSC colorburst-derived crystal (28.636363 MHz —
four times the 3.579545 MHz NTSC colour subcarrier) by 32.

**Field rate and lines per field.** From
`crates/coco-core/src/config.rs:48-63`:

```rust
impl VideoStandard {
    /// Scanlines per field. Provisional (standard video values; see `DESIGN.md` §4).
    pub const fn lines_per_field(self) -> u32 {
        match self {
            VideoStandard::NTSC => 262,
            VideoStandard::PAL => 312,
        }
    }

    /// Nominal field (refresh) rate in Hz.
    pub const fn field_rate_hz(self) -> f64 {
        match self {
            VideoStandard::NTSC => 59.94,
            VideoStandard::PAL => 50.0,
        }
    }
}
```

262 lines at roughly 60 fields/second is standard-definition NTSC — the
same 262 (or 263, split across two interlaced fields, which this emulator
doesn't model) that every NTSC console and computer of the era inherited
from broadcast television. `59.94`, not a clean `60`, is the real NTSC
field rate (color NTSC's frame rate is `30000/1001` fps for backward
compatibility with monochrome broadcasting — a detail 1980s engineers
inherited and 2026 emulator authors still have to type correctly).

Now put the two together the way `Machine::run.rs`'s `cycles_per_field`
does (`crates/coco-core/src/machine/run.rs:185-195`, walked in full in
§6.2's next section) — cycles per field is just clock ÷ field rate:

```
894_886.0 / 59.94  =  14929.09...  →  truncated to u32: 14929 cycles/field
```

And cycles per *line* is that, divided by lines per field. This is where
you have to be careful, because the code does two separate truncating
integer divisions, not one clean one — `cycles_per_field()` truncates to a
`u32` first, and *that* truncated value is what gets divided by
`lines_per_field()` (`run.rs:48`, quoted in §6.3):

```
14929 / 262  =  56.98...  →  truncated: 56 cycles/line
```

**56, not 57.** `DESIGN.md` §4's sketch says "≈ 57 @ 0.895 MHz" as a
back-of-envelope approximation (`894886 / 15734 Hz` horizontal rate ≈ 56.9,
same ballpark) — close enough for a design sketch, but the actual emulator
arithmetic, run through the real constants with the real truncation the
code performs, lands on 56. This is a good habit to build now, in week 6,
before you've internalized which numbers in this codebase are load-bearing
constants and which are conversational approximations in a comment: **when
a design doc and the source disagree by one, trust the source, and go
figure out why.** Here the "why" is boring — floor-division of two
already-floored quantities loses a fraction each time — but it's exactly
the kind of question the debugger (week 16) exists to let you chase down
by inspection instead of by squinting at decimal points.

**PAL**, for comparison, at the same CPU clock (CoCo 1/2 don't support PAL
in this emulator at all — `MachineConfig::validate` rejects the
combination, `config.rs:213-217` — but the arithmetic is worth seeing):

```
894_886.0 / 50.0  =  17897 cycles/field  (truncated)
17897 / 312  =  57 cycles/line  (truncated)
```

Notice PAL's *per-line* number (57) is closer to the DESIGN.md sketch's
"≈57" than NTSC's actual 56 is — a reminder that "same per-line both
standards" (also from that sketch) is approximately true, not exactly.

**The double-speed poke.** If you ever typed `POKE 65497,0` to make BASIC
programs (and every disk access, and the cursor blink) noticeably snappier,
you were flipping the CoCo 3's SAM-compatible R1 speed-select strobe. The
test that pins this down, `crates/coco-core/tests/speed.rs:1-9` (its `use`
lines omitted below):

```rust
//! SAM R1 CPU-rate strobe ($FFD8/$FFD9 — `POKE 65497,0`): true double speed
//! on the CoCo 3. R0 ($FFD6/$FFD7) is inert (SEB Unravelled II Fig 8).

const R0_SET: u16 = 0xFFD7;
const R1_CLEAR: u16 = 0xFFD8;
const R1_SET: u16 = 0xFFD9;
```

`0xFFD9` is decimal 65497 — writing *any* value there (SAM strobes only
care that you touched the address, not what byte you wrote — week 5's
"weird hardware" moment, back again) sets `gime.cpu_fast`. `0xFFD8`
(65496) clears it. If your memory of the "speed poke" pair was
`65497`/`65495`, that's `$FFD9`/`$FFD7` — and `$FFD7` is R0, which SEB
Unravelled II's Figure 8 documents as *wired but inert* on real hardware.
This emulator models that inertness faithfully (`r1_strobes_latch_cpu_speed_and_r0_is_inert`,
`speed.rs:12-25`, writes `R0_SET` last and asserts speed is still off) —
so if you go hunting for the "real" off-poke, `$FFD8`/65496 is the one
that actually does something here, not 65495.

Once `cpu_fast` is set, `cycles_per_field` (`run.rs:185-195`) picks it up:

```rust
fn cycles_per_field(&self) -> u32 {
    // Speed-poke source differs per variant: the GIME's own R1 latch on
    // CoCo 3, the plain SAM's R0|R1 strobes on CoCo 1/2
    // (`docs/coco12-plan.md` Phase 4; `Sam::cpu_fast`'s KNOWN GAP note).
    let cpu_fast = match self.config.variant {
        MachineVariant::Coco3 => self.bus.gime.cpu_fast,
        MachineVariant::Coco1 | MachineVariant::Coco2 => self.bus.sam.cpu_fast(),
    };
    let hz = if cpu_fast { CPU_HZ * 2.0 } else { CPU_HZ };
    (hz / self.config.video.field_rate_hz()) as u32
}
```

Doubling `CPU_HZ` and re-running the same division gives
`(894_886.0 * 2.0) / 59.94 = 29859` cycles/field, `29859 / 262 = 113`
cycles/line — a hair over exactly double 56 (112) for the same
double-truncation reason as before, but close enough that
`tests/speed.rs::speed_poke_doubles_cycles_per_field` asserts the ratio
lands in `1.9..=2.1` rather than pinning an exact integer. **The whole
"double speed" feature, from the emulator's point of view, is one `bool`
changing which branch a single multiplication takes — everything else
downstream (§6.3's `line_budget`) is unaware anything changed.** That's
the payoff of routing every timing decision through one function instead
of scattering `if fast { ... }` checks through the loop, and it's worth
noticing now, because §6.9 exercise 1 has you redo this arithmetic by
hand.

## 6.3 The loop anatomy: `run_field`, `step_instruction`, resumability

Open `crates/coco-core/src/machine/run.rs`. The file-level doc comment
tells you the shape before you read a line of code:

```rust
//! The scanline-driven run loop: `run_field`/`step_instruction` (the
//! resumable per-instruction primitive both are built on), the per-cycle
//! peripheral tick, the per-line trailer, and interrupt servicing.
```

`run_field` — the function everything in this course calls to make the
machine do anything — is almost insultingly short
(`run.rs:20-27`):

```rust
pub fn run_field(&mut self) {
    // Resumable equivalent of the old nested scanline/cycle loops: drive
    // `step_instruction` from wherever the machine is parked until a field
    // completes. On a fresh machine (or right after any previous field —
    // both leave `line`/`line_cycles_spent` at 0) this is exactly one full
    // field from line 0, byte-for-byte identical to the pre-refactor loop.
    while !self.step_instruction().field_complete {}
}
```

One line of actual logic. All the interesting work — line budgets, HALT,
interrupts, hsync, field-sync, audio, the GIME timer — lives inside
`step_instruction`, called over and over until it reports the field is
done. This is worth stopping on, because it's a slightly unusual shape if
you've written a "normal" emulator main loop before (`for line in
0..262 { for cycle in ... { cpu.step() } ; end_of_line() }`, nested loops,
done). The comment tells you why: this *used to be* nested loops, and it
was refactored into a single-instruction-granularity primitive on purpose.

### Why hoist the loop counters into fields?

Look at what moved out of the old nested loops and into `Machine` itself
(`crates/coco-core/src/machine.rs:109-134`), with their doc comments quoted
in full because each one earns its keep:

```rust
/// Current scanline within the field, in `0..lines_per_field`. Was the
/// `for line in 0..lines` counter local to the old `run_field`; hoisting it
/// (with `line_cycles_spent`/`line_budget`) into the machine is what makes
/// execution resumable at instruction granularity. 0 at construction and
/// after every completed field.
line: u32,
/// CPU cycles executed in the current scanline so far. Was `spent` inside
/// the old `run_cycles`. Reset to 0 at each scanline boundary; the
/// invariant after any completed `step_instruction` is
/// `line_cycles_spent < line_budget` (mid-line) or `== 0` (just crossed
/// into a new line/field).
line_cycles_spent: u32,
/// This scanline's cycle budget, sampled once at the line's start (when
/// `line_cycles_spent == 0`) exactly like the old `run_field` sampled
/// `cycles_per_field()/lines` at the top of each loop iteration — so a
/// mid-field speed poke only takes effect on the next line. Also the
/// multiplier the end-of-line GIME timer tick uses. Meaningful only once a
/// line has begun; initialized to 0.
line_budget: u32,
```

A `for` loop's counter dies the moment the loop returns. If `run_field`
were still two nested `for` loops, the only granularity you could ever
stop and resume at is "one whole field" — you could never single-step one
instruction and come back later without re-deriving where you were. By
promoting `line`, `line_cycles_spent`, and `line_budget` from stack-local
loop variables to fields on `Machine`, the *entire run state* becomes part
of the machine's persistent state — which is exactly what a debugger
needs. Week 16's single-instruction step button, its "run until this
scanline" breakpoint, its ability to pause mid-field and inspect
registers without corrupting the timing model — all of that is `run_field`
calling `step_instruction` in a loop with a `break` condition instead of
running to completion. You're looking at the substrate a debugger gets
built on top of, ten weeks before you build the debugger.

### `step_instruction`, in full

`run.rs:42-84`:

```rust
pub fn step_instruction(&mut self) -> StepEvent {
    let lines = self.config.video.lines_per_field();
    loop {
        // Sample this line's budget once, at its start — same point the old
        // `run_field` sampled `cycles_per_field()/lines`.
        if self.line_cycles_spent == 0 {
            self.line_budget = self.cycles_per_field() / lines;
        }
        // Mirror `run_cycles`' `while spent < budget`: run one CPU unit if
        // the line still has budget. For real video timing `line_budget` is
        // always well above one instruction, so this branch always runs;
        // the `else` only guards a degenerate zero-budget line.
        if self.line_cycles_spent < self.line_budget {
            let (cycles, was_instruction) = self.step_cpu_unit();
            self.line_cycles_spent += cycles;
            let kind = if was_instruction {
                StepKind::Instruction { cycles }
            } else {
                StepKind::HaltCycle
            };
            // `run_cycles` exits when spent >= budget; `run_field` then runs
            // the per-line trailer. A single CPU unit (≤ ~20 cycles) can
            // cross at most one ~57-cycle line boundary, so one trailer
            // suffices.
            let field_complete = if self.line_cycles_spent >= self.line_budget {
                let done = self.end_of_line();
                self.line_cycles_spent = 0;
                done
            } else {
                false
            };
            return StepEvent { kind, field_complete };
        }
        // Degenerate zero-budget line (never reached for real timing): no
        // CPU unit to run — do the trailer and continue to the next line so
        // every call still makes forward progress.
        let field_complete = self.end_of_line();
        self.line_cycles_spent = 0;
        if field_complete {
            return StepEvent { kind: StepKind::HaltCycle, field_complete: true };
        }
    }
}
```

Trace one call through it. `line_cycles_spent == 0` at the start of a line
(true on the very first call, and true right after `end_of_line` resets
it), so the budget gets (re-)sampled — this is the one and only place
`cycles_per_field()` is consulted, and it's consulted fresh every line, so
a mid-field `POKE 65497,0` takes effect on the *next* line, never
retroactively on the line already in progress. Then one "CPU unit" runs
(§6.4 — either an instruction or a burned HALT cycle), its cost is added
to `line_cycles_spent`, and *if that pushes the line over budget*,
`end_of_line()` (§6.5) runs immediately, in the same call, before
`step_instruction` returns. The comment is explicit that this ordering is
"load-bearing and preserved exactly from the old code" — the per-line
trailer must run before any instruction of the next line gets to execute,
because that trailer is what raises the very interrupts the next
instruction might need to see.

### `StepEvent`/`StepKind`: what one call reports

`crates/coco-core/src/machine.rs:137-164`:

```rust
/// What a single [`Machine::step_instruction`] advanced. Both fields are
/// reported because one call can retire an instruction (or burn a HALT* cycle)
/// AND cross a scanline/field boundary in the same step — the debugger's
/// `run_until` needs the CPU action for its trace ring and the field flag for
/// its stop condition.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct StepEvent {
    /// What the CPU did this step.
    pub kind: StepKind,
    /// True when this step completed a video field: the per-scanline trailer
    /// for the field's last line ran, `line` wrapped back to 0, and the
    /// framebuffer was rendered — exactly the point the old `run_field`
    /// returned.
    pub field_complete: bool,
}

/// The CPU action a [`Machine::step_instruction`] performed.
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum StepKind {
    /// One instruction retired, consuming `cycles` bus cycles.
    Instruction {
        /// Bus cycles the instruction consumed.
        cycles: u32,
    },
    /// One HALT* cycle was burned (the cartridge holds the bus low); the CPU
    /// did not advance and no instruction retired.
    HaltCycle,
}
```

> **Rust corner: an enum with payload beats two bools.** A more
> C-flavored design would give `step_instruction` two output parameters:
> `was_halt_cycle: bool` and `cycles: u32` (meaningless when the bool is
> true), plus a third `field_complete: bool`. That's three loosely related
> facts, one of which is sometimes garbage, glued together by convention
> instead of the type system. `StepKind` makes the illegal state
> unrepresentable: you cannot construct a `StepKind::HaltCycle { cycles }`
> — the variant simply has no such field — so a caller matching on `kind`
> can never accidentally read a cycle count that doesn't apply. This is
> the same idea as `Option`/`Result` (which you already use), just applied
> to a domain-specific pair of outcomes instead of a generic library type.
> `#[derive(Clone, Copy, Debug, PartialEq, Eq)]` gives both types value
> semantics and comparability for free — no method bodies to write, and
> notice `Copy`: these are small enough (`StepKind` is at most a `u32` plus
> a discriminant) that cloning is cheaper than borrowing, so the derive
> lets callers use them like `i32`s without a second thought.

## 6.4 `step_cpu_unit`: HALT, then interrupts, then the CPU, then peripherals

`step_instruction` calls one private helper per "unit" of work,
`run.rs:86-123`:

```rust
/// One iteration of the old `run_cycles` inner loop: burn a HALT* cycle or
/// execute one instruction, then tick the per-cycle peripherals. Returns
/// `(cycles, was_instruction)`.
///
/// The cartridge HALT* line has priority over everything (MC6809 pin
/// behaviour): while a device holds it — the FD-502's sector-transfer
/// handshake — the CPU sits at an instruction boundary burning cycles and
/// pending interrupts wait. The cartridge is ticked either way so it can
/// pace the very work (DRQ cadence) that releases the line.
///
/// The MC6809 recognizes interrupts only at the *end* of an instruction, so
/// the first instruction after HALT* releases must execute before any
/// pending NMI/IRQ/FIRQ is serviced. Skipping this lets the completion NMI
/// of an FD-502 sector read preempt the DSKCON copy loop's `STB ,X+` that
/// stores the sector's final byte — dropping one byte per sector on load.
fn step_cpu_unit(&mut self) -> (u32, bool) {
    let (cycles, was_instruction) = if self.bus.halt_asserted() {
        self.prev_halted = true;
        (1, false)
    } else {
        // Coming straight out of HALT, run one instruction before
        // acknowledging interrupts (they stay pending for next loop).
        if !self.prev_halted {
            self.bus.poll_cart_interrupt();
            if self.bus.take_nmi() {
                self.cpu.nmi(&mut self.bus);
            }
            self.service_interrupts();
        }
        self.prev_halted = false;
        (self.cpu.step(&mut self.bus), true)
    };
    self.bus.cart.tick(cycles);
    self.bus.cassette.tick(cycles, self.bus.pia1.a.c2_output());
    self.bus.bitbanger.tick(cycles, self.bus.pia1_tx_mark());
    self.bus.cycle_clock = self.bus.cycle_clock.wrapping_add(u64::from(cycles));
    (cycles, was_instruction)
}
```

Read the branches top to bottom, because the order encodes real hardware
priority, not just code convenience:

1. **HALT check first.** `self.bus.halt_asserted()` asks whether the
   cartridge port is holding the CPU's HALT* pin low — on a stock CoCo 3
   the only device that ever does this is the FD-502 disk controller
   mid-sector-transfer (full story in week 13). If it is, the CPU doesn't
   run at all: one cycle is "burned" (`(1, false)` — no instruction
   retires), `prev_halted` is set, and control falls straight through to
   the peripheral ticks at the bottom. This matches the real 6809E pin
   behaviour: HALT* has priority over everything, including interrupts.
2. **Interrupt polling, but only if we weren't halted last time.** The
   `if !self.prev_halted` guard is the subtle part, and the doc comment
   explains the hardware reason in full: the MC6809 recognizes interrupts
   only *between* instructions, never mid-instruction. The instant HALT*
   releases, the very next thing that must happen is the CPU actually
   *running an instruction* — not immediately vectoring off to service
   whatever NMI/IRQ/FIRQ arrived while it sat there. Get this backwards
   and you reproduce a real, specific, nasty bug: the FD-502's
   end-of-sector NMI preempts the disk driver's final `STB ,X+` that
   writes the sector's last byte, and every sector loaded from disk is
   missing its last byte. `prev_halted` is exactly one bit of memory
   carried across calls to enforce "run one instruction before
   re-arming interrupt recognition" — a preview of week 13's HALT/NMI
   handshake, but the ordering decision is made here, in week 6's file.
3. **When interrupts are polled, the order is: cartridge level interrupt,
   then NMI, then IRQ/FIRQ** (`poll_cart_interrupt`, `take_nmi`,
   `service_interrupts` — §6.6 covers what each of those does).
4. **`self.cpu.step(&mut self.bus)`** — the actual instruction, the thing
   weeks 2–4 built.
5. **Peripheral ticks, unconditionally, using whatever `cycles` this unit
   consumed** (1 for a HALT cycle, the real instruction cost otherwise):
   the cartridge (so DRQ pacing keeps moving even while halted — read the
   doc comment again: "The cartridge is ticked either way so it can pace
   the very work... that releases the line" — if you *didn't* tick it
   while halted, the machine would halt forever, since nothing would ever
   satisfy the condition that releases HALT*), the cassette motor/FSK
   decoder (week 12), the bit-banger serial line (week 14), and the
   machine-wide `cycle_clock` used for audio timestamping (week 11).

> **Rust corner: `pub(super)`.** `end_of_line` (next section) is declared
> `pub(super) fn end_of_line(&mut self) -> bool` — visible to `run.rs`'s
> parent module (`machine.rs`, which does `mod run;`) and everything else
> under it, but not to `coco-egui` or any other crate. This is Rust's
> answer to "protected, but only within one directory of the tree," and
> it's how `machine/` stays split into focused files (`run.rs`,
> `render.rs`, `audio.rs`, `video_mode.rs`, all `mod`-declared in
> `machine.rs`) without every cross-file helper becoming `pub` and part of
> the crate's public API by accident. Grep the module for `pub(super)` as
> you read it — it's a reliable signal of "this exists to be called from a
> sibling file in the same subsystem, not from outside it."

## 6.5 `end_of_line`: the per-scanline trailer

`run.rs:130-172`, the function `step_instruction` calls the instant a
line's cycle budget is exhausted:

```rust
pub(super) fn end_of_line(&mut self) -> bool {
    let lines = self.config.video.lines_per_field();
    let fs_falling_line = self.config.video.fs_falling_line(self.config.variant);
    let fs_rising_line = self.config.video.fs_rising_line(self.config.variant);
    self.bus.hsync();
    if self.line == fs_falling_line {
        self.bus.fs_falling();
    }
    if self.line == fs_rising_line {
        self.bus.fs_rising();
    }
    self.render_scanline();
    // Render this line's audio to the oversampled stereo grid,
    // self-capping when nothing drains it.
    if self.audio_buffer.len() >= super::AUDIO_BUFFER_CAP {
        self.audio_buffer.clear();
    }
    self.flush_line_audio();
    // GIME interval timer: TINS=1 counts the fixed 3.58 MHz clock — 4 ticks
    // per normal-speed CPU cycle, 2 per double-speed cycle — TINS=0 counts
    // horizontal syncs (1 per line). No such timer exists on the plain-SAM
    // path (CoCo 1/2) — the GIME stays completely inert there
    // (`docs/coco12-plan.md` Phase 4). `line_budget` is this line's sampled
    // cycle count — the old loop's `cycles_per_line`.
    if self.config.variant == MachineVariant::Coco3 {
        let ticks = if self.bus.gime.timer_is_fast() {
            let per_cycle =
                FAST_TIMER_TICKS_PER_CPU_CYCLE / if self.bus.gime.cpu_fast { 2 } else { 1 };
            self.line_budget * per_cycle
        } else {
            1
        };
        self.bus.gime.tick_timer(ticks);
    }
    self.line += 1;
    if self.line >= lines {
        self.line = 0;
        self.render_field();
        true
    } else {
        false
    }
}
```

Every scanline gets `hsync()` (horizontal sync — this alone pulses PIA0
CA1, more in §6.6). Only two specific scanlines, out of the whole field,
get the field-sync pulses — and unlike a naive "one big vsync pulse at the
very end of the field" design, the CoCo's field sync is genuinely **two
separate edges**, falling and rising, sitting mid-field on real NTSC
timing. `config.rs` pins the exact scanline numbers, derived from MAME's
own timing constants (`config.rs:65-111`):

| Edge | NTSC, CoCo 3 | NTSC, CoCo 1/2 | Source |
|------|:---:|:---:|---|
| Falling (`fs_falling_line`) | **244** | **216** | MAME `gime.cpp` border-sum vs. `mc6847.cpp` directly |
| Rising (`fs_rising_line`) | **248** | **248** | MAME `mc6847.cpp` `LINES_UNTIL_RETRACE_NTSC` + `LINES_VERTICAL_RETRACE` − 1 |

Notice the CoCo 3 and CoCo 1/2 fall at *different* lines (244 vs. 216) —
the GIME's own border-geometry math (top border + active display + part of
bottom border, `+1`) doesn't match the plain MC6847's number, and the code
keeps both rather than picking one and hoping. The rising edge, by
contrast, is the same 248 for every variant, because its derivation cites
the MC6847's own timing constants directly rather than a GIME-specific
approximation — the doc comment on `fs_rising_line` is candid that this is
"absent a source that shows the GIME diverging... on this edge the way it
does on the falling one," i.e., an honest "we haven't found evidence it's
different" rather than "we've confirmed it's the same." PAL's edges are
marked `UNVERIFIED` outright and collapsed to the last scanline of the
field rather than guessed — and since `MachineConfig::validate` rejects
CoCo 1/2 + PAL entirely, the PAL branch is only ever reached by a CoCo 3,
where the same "not confirmed" caveat applies. This is a good specimen of
the course's recurring theme (Appendix A): when the authoritative sources
disagree or fall silent, the honest move is a code comment that says so,
not a silently confident wrong number.

After sync comes video (`render_scanline`, week 7's subject — CoCo 3 native
modes paint scanline-by-scanline through `field_scan`; legacy VDG text is a
whole-frame snapshot taken at `render_field`), then audio
(`flush_line_audio`, week 11 — note the self-capping `AUDIO_BUFFER_CAP`
check right before it, so a headless test that never drains audio can't
leak memory across a 1500-field boot like the one in §6.7), then the GIME
timer (week 8's territory, shown here only because it lives in the trailer
— notice it's gated on `MachineVariant::Coco3`, keeping the GIME
"completely inert" on the CoCo 1/2 plain-SAM path, per `line += 1` finally
advancing the scanline counter and, on wraparound, rendering the finished
field and returning `true` — the signal `step_instruction` propagates all
the way out to `run_field`'s `while` condition.

## 6.6 Interrupt plumbing: the wired-OR, and a debugging war story

### The wire

Two chips can each independently want the CPU's attention, and the 6809
has exactly two maskable interrupt pins (IRQ, FIRQ) to receive them on.
Real hardware solves this the way you'd solve it with two switches and one
light bulb: wire them in parallel. `crates/coco-core/src/bus/sync.rs:10-26`:

```rust
/// True when any interrupt source is holding the CPU IRQ line low.
///
/// PIA0's output and the GIME's IRQ output are wired-OR on the CPU pin: at
/// the BASIC prompt the stock ROM runs the legacy PIA path (INIT0 IEN=0)
/// off PIA0's field/horizontal sync, while GIME-native software enables
/// IEN and the $FF92 sources instead (`DESIGN.md` §4).
pub fn irq_asserted(&self) -> bool {
    self.pia0.irq() || self.gime.irq_asserted()
}

/// True when any interrupt source is holding the CPU FIRQ line low: PIA1
/// (the legacy cartridge FIRQ path) wired-OR with the GIME's FIRQ output
/// ($FF93 sources gated by INIT0 FEN).
pub fn firq_asserted(&self) -> bool {
    self.pia1.irq() || self.gime.firq_asserted()
}
```

`||` *is* the wired-OR — both boolean expressions get evaluated (Rust's
`||` short-circuits, so `gime.irq_asserted()` isn't even called once
`pia0.irq()` is already `true`, which is harmless here since neither call
has side effects worth skipping), and the CPU never learns *which* source
asserted the line, exactly as on real silicon: an interrupt pin is a
level, not a labeled event. `service_interrupts` (`run.rs:174-183`,
called from `step_cpu_unit`) is what actually delivers it:

```rust
/// Deliver pending FIRQ/IRQ to the CPU. The CPU itself honours the F/I masks
/// and leaves a masked, still-asserted line pending for the next check.
fn service_interrupts(&mut self) {
    if self.bus.firq_asserted() {
        self.cpu.firq(&mut self.bus);
    }
    if self.bus.irq_asserted() {
        self.cpu.irq(&mut self.bus);
    }
}
```

`cpu.firq`/`cpu.irq` are week 4's territory — they check the CPU's own F/I
mask bits and no-op if masked, leaving the bus line asserted for next
time. This function just re-checks the wired-OR every single instruction
boundary and offers the CPU a chance to act on it.

### How one edge becomes a flag: `PiaPort::set_c1`

The PIA side of the wire needs one more piece: turning a *level* (field
sync is a physical line that goes low then high) into a *latched flag*
the CPU can poll and clear by reading a register. `crates/coco-core/src/pia.rs:66-85`:

```rust
/// Drive the Cx1 line to `level`, latching the Cx1 flag only on a real
/// transition whose direction matches CRA/CRB bit 1 ([`cr::C1_EDGE_HIGH`]):
/// bit1=1 selects low→high, bit1=0 selects high→low. A call that repeats
/// the current level (no edge) never sets the flag, and an edge in the
/// non-selected direction doesn't either — matching MAME `6821pia.cpp`
/// `c1_low_to_high`/`c1_high_to_low` (~line 1107): the flag sets iff
/// `(m_in_c1 != state) && ((state && rising_selected) || (!state &&
/// falling_selected))`. The CoCo wires horizontal sync to PIA0 CA1 and
/// field sync to PIA0 CB1.
pub fn set_c1(&mut self, level: bool) {
    let transitioned = self.c1_level != level;
    self.c1_level = level;
    if !transitioned {
        return;
    }
    let rising_selected = self.control & cr::C1_EDGE_HIGH != 0;
    if level == rising_selected {
        self.control |= cr::C1_FLAG;
    }
}
```

`bus.fs_falling()` (`sync.rs:119-125`) calls `self.pia0.b.set_c1(false)` at
line 244 (CoCo 3 NTSC); if PIA0's control register B has selected the
falling edge (the stock ROM's default — `cr::C1_EDGE_HIGH` clear), the Cx1
flag bit latches, and `PiaPort::irq()` (a private helper checked by the
public `MC6821::irq()`, `pia.rs:181-183`) now reports true until something
*reads* PIA0's port-B data register, which (week 10 has the full story)
clears the flag as a side effect of the read — the very fact that forced
`Bus::read` to take `&mut self` back in week 1. That's the whole chain,
four function calls deep: `end_of_line` → `bus.fs_falling()` →
`pia0.b.set_c1(false)` → `pia0.irq()` → `bus.irq_asserted()` →
`service_interrupts` → `cpu.irq(&mut bus)`.

### The war story

Here's the discovery `DESIGN.md` §4 documents under a dated implementation
note, and it's worth telling as what it actually was: a debugging session
where an emulator that was doing everything *correctly* still produced a
machine that looked *dead*.

> **Implementation note (2026-07, verified against the real ROM):** the
> stock CoCo 3 sits at the BASIC prompt with **INIT0 IEN=0/FEN=0**, i.e.
> the *legacy PIA path*, not the GIME interrupt block. The 60 Hz field
> sync is wired to **PIA0 CB1** (`$FF03`) and horizontal sync to **PIA0
> CA1** (`$FF01`); both drive IRQ. That field-sync IRQ is what breaks the
> ROM out of its `BRA *` idle loop.

Picture building this emulator in the natural order: CPU first (correct —
weeks 2-4 proved it against hand-traced flags and cycle counts), bus and
memory decode second (correct — week 5's `bus_map.rs` tests all pass), the
shiny new GIME chip's own interrupt controller third, because that's the
*interesting*, headline chip you set out to build ("I'd like to start with
emulating the GIME," to quote this very course's own founding request in
`CLAUDE.md`). You wire the GIME's `$FF92`/`$FF93` IRQ/FIRQ enable registers
correctly. You boot real Color BASIC. The CPU executes millions of
instructions — you can single-step it and watch registers change exactly
as documented, cycle-for-cycle right by every measure you have. And the
screen just sits there. No cursor blink, no sign-on banner update, no
input accepted. Every fact about the CPU is correct and the *machine* is
frozen — which is a uniquely disorienting bug, because the obvious
question "is the CPU broken?" has an unambiguous, frustrating "no."

The resolution is the note above: BASIC's idle loop (a literal `BRA *` —
branch to self, spin forever) is *designed* to be interrupted. It doesn't
poll a flag in a loop; it sits doing nothing and trusts an interrupt
handler to do the housekeeping (blink the cursor, check the keyboard) and
`RTI` back into the spin. On real hardware and in the ROM's actual
power-on configuration, that interrupt is **not** routed through the fancy
new GIME interrupt block you just finished building — `$FF92`'s IEN bit
is off. It's routed through the boring, decades-older MC6821 PIA0, exactly
the way a plain CoCo 1 would do it, because Motorola's and Tandy's ROM
authors kept the legacy path as the CoCo 3's power-on default for
compatibility. Skip modeling PIA0's field-sync IRQ — reasonable, if you're
following "GIME first" as the obvious build order — and you get a
simulator that is instruction-perfect and functionally comatose. This is
exactly why the reading order in this course puts the bus and the humble
PIA (week 10, in depth) ahead of the GIME's native video and interrupt
block (weeks 7-9): the thing that actually makes BASIC alive is not the
glamorous chip.

## 6.7 The lab: booting real Color BASIC, headless, in a test

`crates/coco-core/tests/coco1_boot.rs` is this week's textbook exercise —
it drives `run_field` for real, from cold reset, against a real ROM image,
with no window, no GPU, and no human. Walk it top to bottom.

**Loading the ROM.** `try_load` (`coco1_boot.rs:28-33`) reads
`roms/bas12.rom` relative to the workspace root — Color BASIC 1.2, the
CoCo 1's ROM, *without* Extended Color BASIC. `boot_machine`
(`coco1_boot.rs:38-59`) composes a 32K flat image: `$FF` open-bus filler
for the low 8K (where Extended BASIC would live), the real `bas12.rom`
bytes at the high 8K (`$A000-$BFFF`), then constructs a `Machine` with
`MachineVariant::Coco1`, `VideoStandard::NTSC`, `MemorySize::K32`, no
monitor (a CoCo 1 has no RGB/composite port — RF only), `VDGVariant::MC6847`.

**Driving time.** The test's core loop is almost embarrassingly plain
(`coco1_boot.rs:109-117`):

```rust
const MAX_FIELDS: usize = 1500;
let mut alive = false;
for _ in 0..MAX_FIELDS {
    m.run_field();
    if screen_contains(&mut m, "OK") && screen_contains(&mut m, "COLOR BASIC 1.2") {
        alive = true;
        break;
    }
}
```

That's it. `run_field()` is called up to 1500 times — 1500/59.94 ≈ 25
seconds of emulated wall-clock time, generous headroom for a cold boot —
and after every field the test peeks at the screen. No special-cased "wait
for boot" hook exists or is needed; `run_field` is the entire API surface
a caller needs to make time pass correctly, sync pulses and all.

**Reading the screen without a framebuffer.** `screen_contains`
(`coco1_boot.rs:61-63`) calls `m.text_screen_lines()`
(`crates/coco-core/src/machine/video_mode.rs:92-112`), which does *not*
read the RGBA framebuffer at all — it walks the legacy VDG text screen
directly out of RAM, through the bus (honouring the MMU, though a CoCo 1
has none), decoding each byte with the same `video::decode_alpha_char`
the real renderer uses (so the test can never see something different
from what a screen would actually show):

```rust
pub fn text_screen_lines(&mut self) -> Vec<String> {
    match self.video_mode() {
        VideoMode::CocoText | VideoMode::CocoGraphics => {
            let base = self.legacy_display_base();
            (0..video::ROWS as u16)
                .map(|row| {
                    (0..video::COLS as u16)
                        .map(|col| {
                            let addr = base.wrapping_add(row * video::COLS as u16 + col);
                            video::decode_alpha_char(self.bus.read(addr))
                        })
                        .collect()
                })
                .collect()
        }
        // ...
    }
}
```

This is the headless-testability payoff `DESIGN.md` and week 1 promised:
"the machine you can PEEK" is available to a `#[test]` function exactly as
it was available to your own `PEEK` statements at the BASIC prompt, no
pixels or GPU required — 32 columns × 16 rows of decoded ASCII, straight
out of RAM.

**Typing.** Once the sign-on banner and `OK` prompt appear, the test types
`PRINT 2+2` by driving the actual keyboard matrix (week 10's subject),
holding each key down for 3 fields and released for 3 more
(`tap_char`/`type_line`, `coco1_boot.rs:69-90`) — long enough for the ROM's
own debounced scan loop, running off the very field-sync interrupt §6.6
just explained, to see it:

```rust
fn tap_char(m: &mut Machine, c: char) {
    let (pos, shift) =
        coco_core::keyboard::char_key(c).unwrap_or_else(|| panic!("no key for {c:?}"));
    if shift {
        m.bus.keyboard.set(coco_core::keyboard::SHIFT, true);
    }
    for _ in 0..3 {
        m.bus.keyboard.set(pos, true);
        m.run_field();
    }
    m.bus.keyboard.set(pos, false);
    m.bus.keyboard.set(coco_core::keyboard::SHIFT, false);
    for _ in 0..3 {
        m.run_field();
    }
}
```

Then it waits (up to `ANSWER_FIELDS = 120` more fields) for `" 4"` — the
leading space is Color BASIC's own formatting for a positive numeric
result — to show up anywhere on screen, and asserts.

### Run it yourself — and a note on what you'll actually see

```
cargo test -p coco-core --test coco1_boot
```

Be honest with yourself about what happens on this machine, because it's
an important lesson about test hygiene, not a problem with the test. Run
it, and you'll see:

```
test coco1_boots_color_basic_only_and_evaluates_print ... ok
```

That "ok" is **not** proof the boot succeeded. `bas12.rom` is not present
in `roms/` in this worktree — `.gitignore` excludes `/roms/*` outright
(real ROM dumps are copyrighted, unlike this codebase's own source — the
course README's Appendix B is the place that spells out why ROMs and code
get different legal treatment), and even the "local resources present on
this machine" this course's `CLAUDE.md` documents only lists
`coco3.rom` and `disk11.rom` — Color BASIC 1.2 specifically isn't
guaranteed to be sitting around even on an author's own machine. `boot_machine`
handles this by *not failing*: it prints a message and the test function
returns early —

```rust
fn boot_machine() -> Option<(Machine, Vec<u8>)> {
    let Some(bas) = try_load("bas12.rom") else {
        eprintln!(
            "skipping coco1_boot: bas12.rom not present in roms/ (see docs/coco12-plan.md \"ROM files\")"
        );
        return None;
    };
    // ...
}

#[test]
fn coco1_boots_color_basic_only_and_evaluates_print() {
    let Some((mut m, _bas_rom)) = boot_machine() else {
        return;
    };
    // ... the entire test body above never runs
}
```

Cargo's test harness has no first-class "skipped" state for a plain `fn`
test (that would need `#[ignore]`, which behaves differently — an ignored
test doesn't even run by default) — so a test that early-returns reports
"ok" exactly the same as a test that ran to completion and passed every
assertion. Verify this for yourself, because it's the only way to actually
see the skip happen:

```
cargo test -p coco-core --test coco1_boot -- --nocapture
```

```
skipping coco1_boot: bas12.rom not present in roms/ (see docs/coco12-plan.md "ROM files")
test coco1_boots_color_basic_only_and_evaluates_print ... ok
```

If you have a legally-obtained `bas12.rom` (Color BASIC 1.2, 8KB), drop it
in `roms/` and re-run — now `alive`/`answered` really are being computed,
and a real ~25-second-of-emulated-time boot, keystroke injection, and
screen assertion happens inside a `cargo test` invocation that takes a
fraction of a second of *wall* time, because your host CPU is thousands of
times faster than 894,886 Hz. Either way, you've now read (and can predict
the exact behaviour of) every line standing between `Machine::new` and a
working `PRINT 2+2` — whether or not this particular machine can prove it
to you today.

Every device this course has built so far — the CPU, the bus, the PIA's
Cx1 latch — has been necessary but, until this week, silent: correct
values with no clock driving them into view. `run_field` is what turns

CoCo 3 BASIC screen you're about to reproduce isn't drawn by the GIME's
flagship native video hardware at all — it's the old MC6847 VDG's text
mode, faithfully imitated, one more example of the machine's history
outliving its successor chip.
